# 향후 작업 (규모 확장 시)

지금 당장은 불필요하지만, 팀/데이터 규모가 커지면 필요해지는 작업을 여기 기록한다. 트리거 조건에 해당하기 전까지는 우선순위를 낮게 둔다.

## 1. Firestore 쿼리 범위 제한 + 로딩 상태 UI

### 현재 상태

`lib/store.tsx`가 앱 시작 시 아래 두 컬렉션을 필터 없이 통째로 구독한다.

- `onSnapshot(collection(db, REQUESTS_COL))` — 창립 이후 전체 휴가 신청 이력
- `onSnapshot(collection(db, GRANTS_COL))` — 창립 이후 전체 부여/차감 이력

그래서 로그인한 모든 유저가 매번 전체 이력을 다운로드한다. 지금 팀 규모(신청 건수 수백 건 이하)에서는 첫 스냅샷 응답이 보통 수십~200ms 안팎이라 체감 지연이 거의 없다. 대신 대시보드/Team Overview/승인 페이지는 이 첫 스냅샷이 오기 전까지 빈 데이터로 렌더링된 뒤 갑자기 채워지는 팝인(pop-in)이 있다 — 로딩 스피너나 스켈레톤 UI가 없어서다(`app/employees/page.tsx`만 예외적으로 자체 `loading` state가 있음).

### 왜 지금은 안 하는지

- 데이터 양이 적어 로딩 스피너를 넣을 정도로 체감되는 지연이 없음
- 로딩 UI만 따로 넣는 건 근본 해결이 아니라 증상만 가리는 것 — 진짜 필요해지는 시점엔 쿼리 범위 제한이 먼저고, 로딩 UI는 그 작업의 자연스러운 부산물로 같이 넣는 게 맞음

### 재검토 트리거

아래 중 하나라도 해당하면 다시 꺼내볼 것:

- 직원 수가 크게 늘어남 (예: 30명 이상)
- 누적 휴가 신청 건수가 수천 건대로 늘어남
- 실사용자가 로딩 지연을 체감했다는 피드백이 들어옴
- Firestore 읽기 비용이 유의미하게 증가함 (전체 구독 방식이라 인원/이력이 늘수록 읽기 비용도 같이 늘어남)

### 재검토 시 할 일

1. `REQUESTS_COL`/`GRANTS_COL` 구독을 기간(예: 최근 1~2년) 또는 유저 단위로 제한하거나 페이지네이션 도입
   - `lib/grantLedger.ts`의 `calcUsedLeave`, `simulateBaseConsumption` 등은 회계연도 시작일 이후 이력만 있으면 계산 가능 — 범위 제한 시 이 기준(`currentLeaveYearStart`)에 맞춰 쿼리 범위를 잡으면 계산 로직은 그대로 유지 가능
   - 다만 부여 연차 이력 열람(`app/employees/page.tsx`의 "부여 이력" 모달)처럼 전체 이력 조회가 필요한 화면은 별도 쿼리로 분리해야 함
2. 대시보드/Team Overview/승인 페이지에 초기 로딩 상태(스피너 또는 스켈레톤) 추가 — 1번 작업과 함께 진행

## 2. 승인자 권한을 부서 단위로 분리

### 현재 상태

승인 권한은 `User.isManager` 불리언 하나뿐이다(`lib/types.ts`). `isManager`가 true면 부서 상관없이 전 직원의 휴가 신청을 다 승인/반려할 수 있다(`app/approval/page.tsx`). 부서별로 승인자를 나누는 개념 자체가 없다.

### 왜 지금은 안 하는지

지금 팀 규모에서는 매니저가 소수고, 전체를 다 보는 게 오히려 자연스럽다. 부서 단위로 승인 권한을 쪼개면 관리자 역할/권한 스키마를 새로 설계해야 하는데(`isManager` 불리언 → 부서별 권한 구조로 전환), 지금 필요하지 않은 복잡도를 미리 넣는 것 — 2026-08-24 기준 논의에서 "지금은 이 구조로 충분함"으로 결론 내림.

### 재검토 트리거

- 부서 수/인원이 늘어나 한 매니저가 전체 신청을 파악하기 어려워짐
- 부서마다 승인자를 따로 두고 싶다는 요구가 실제로 생김
- 매니저가 여러 명으로 늘면서 "누가 이 신청을 승인해야 하는지"가 모호해지는 사례 발생

### 재검토 시 할 일

- `User`에 부서별 승인 권한(예: `approverDepartments: string[]` 또는 별도 역할 컬렉션) 추가
- `app/approval/page.tsx`의 신청 목록 필터링을 로그인한 승인자의 담당 부서 기준으로 제한
- "전체관리자"(모든 부서 승인 가능) 등급을 별도로 둘지, 부서장 승인만 둘지 결정 필요 — 처음 논의 때 나온 대안: `isManager` 외에 "전체관리자" 등급을 따로 두고 일반 매니저는 자기 부서만 승인 가능하게 하는 구조

## 3. 월별/연도별 팀 통계 대시보드

### 현재 상태

`app/employees/page.tsx`에 전체 인원 합산 통계(총 연차/전체 사용/전체 잔여)는 있지만, 부서별 소진율이나 월별 사용 추이, 특정 기간 동시 휴가자 수 같은 관리자용 인사이트는 없다.

### 왜 지금은 안 하는지

지금은 부서가 실질적으로 나뉘어 있지 않은 통합 조직이라("팀도 안 나눠져 있고 부서도 통합", 2026-08-24 논의) 부서별 통계를 만들어도 의미가 없다. `LeaveRequest.department` 필드 자체는 존재하지만 실제 조직 구조를 반영한 값이 아님.

### 재검토 트리거

- 실제로 팀/부서가 나뉘어 운영되기 시작함
- 인원이 늘어 특정 기간에 누가 몇 명이나 동시에 자리를 비우는지 관리자가 파악하기 어려워짐
- 월별/분기별 연차 소진 추이를 보고서로 뽑아야 하는 요구가 생김

### 재검토 시 할 일

- 조직 구조(부서/팀)를 실제로 반영하는 필드·화면 정비가 선행되어야 함 — 지금의 `department` 필드를 신뢰할 수 있게 만드는 작업이 먼저
- 부서별 소진율 breakdown, 월별 사용량 추이 차트, 특정 기간 동시 휴가자 리스트 등을 관리자 대시보드에 추가
